# playbook: מריפו של מנחה לאתר חי, שלב אחרי שלב

המדריך הזה מסכם איך נבנה Lavender Bakery Copilot, כדי לחזור על התהליך בפרויקטים הבאים.

## 0. לפני שמתחילים
1. **פרויקט אחד = תיקייה אחת = ריפו אחד = סשן Claude אחד.** פותחים את הסשן בתוך התיקייה של הפרויקט, כבר בהתחלה.
2. קוראים את דרישת המנחה, ורושמים בשורה אחת מה בדיוק צריך להגיש.
3. כשהמשימה משתנה מהותית, פותחים ריפו חדש, ולא דוחסים לישן.

## 1. לקחת את הריפו של המנחה
1. ריפו ציבורי חדש בגיטהאב.
2. commit ראשון: הקוד של המנחה כמו שהוא. ככה רואים אחר כך בדיוק מה שינינו.
3. המסמכים של המנחה (spec, architecture, practice) נשארים בתיקייה הראשית, כי הקוד מפנה אליהם. עותק מקורי ב-`reference/`.
4. להתקין רק מה שצריך, באישור (Python, Node).

## 2. להפוך אותו לשלך
1. כל שינוי בענף נפרד ו-PR: עיצוב, שפה, פרומפט והגדרות.
2. להריץ את האתר במחשב ולבדוק אותו בעיניים, גם ברוחב של טלפון.
3. באג שנמצא בקוד המקורי הופך ל-issue עם תווית `bug`.
4. לעדכן את המסמכים באותו PR, כולל טבלת ההחלטות ב-`architecture.md`.

## 3. Railway
1. `railway init`, ואז Postgres, ואז שירותי `web` ו-`digest` מהריפו.
2. **להתקין את אפליקציית Railway בגיטהאב לפני שיוצרים את השירותים**, רק לריפו הזה. אם השירותים נוצרו לפני כן: Disconnect ו-Connect Repo בכל שירות.
3. `npm install --prefix .railway`, ואז `railway config plan` (מציג), ואז `railway config apply` (מבצע).
4. משתנים: הגדרות רגילות בפקודה, וסודות מוזנים רק על ידי בעלת הפרויקט.
5. Generate Domain, ואז בדיקת `/health`.
6. Source: ענף `main`, Auto deploy ו-Wait for CI.
7. **כל שינוי הגדרה באתר של Railway נרשם מיד ב-`railway.ts`**, עד ש-`railway config plan` אומר "already up to date".

## 4. בדיקות
1. tests בכל PR (מודל מדומה).
2. evals מול המודל האמיתי: המפתח בכספת של גיטהאב (Secrets), ו-`MODEL` ב-CI זהה לזה שבאתר.
3. evals עם מילים בעברית, ולא רק באנגלית.
4. **בדיקה באתר החי אחרי כל מיזוג.** שם נמצאו הבאגים האמיתיים: הצעה שהבוט לא יכול לקיים, "תאריך עתידי", "גיליון" שלא קיים, ומטבע.
5. כשמשהו אוטומטי לא קורה, קודם בודקים את דפי הסטטוס: githubstatus.com, status.railway.com, status.anthropic.com.

## 5. לפני ההגשה
1. **לפתוח כל קובץ שהמנחה יראה**, מנקודת המבט שלו: README, spec, architecture, practice ו-About.
2. לוודא שהגרסה באתר היא הגרסה האחרונה של `main`.
3. לחפש סודות בכל ההיסטוריה.
4. פסקת "להגשה" בראש ה-README: קישור לאתר, מה שיניתי, מה מצאתי, ובאגים ידועים.
5. הסיסמה נשלחת בנפרד, לעולם לא בריפו.
6. אין "אחרי ההגשה": כל מה שנמצא מתוקן, או מתועד ב-issue.
